What this does

    How to use it

    1. Open your project in Supabase, then SQL Editor → New query.
    2. Paste the SQL and click Run. Do one table at a time.
    3. Check Authentication → Policies for older policies on the same table and delete any you don't want. Policies add up, so an old using (true) policy still lets everyone in.
    4. Test it: log out of your app and check the data is gone, then log in as a second user and check you can't see the first user's rows.

    If your app was built with Lovable, Bolt or Cursor, you can copy the prompt version instead. It tells the AI not to "fix" any error by switching RLS off, which is the most common way these settings get undone.

    Why the grants are there

    From 30 October 2026, new tables in existing Supabase projects are no longer opened to the Data API automatically: they need a grant before your app can reach them. The SQL above grants only what each pattern needs, and removes access for logged-out visitors (anon) wherever they shouldn't have it. Tables you created before the change keep their old grants, so running this on them tightens access too. More on the 30 October change.

    Questions

    How do I write a Supabase RLS policy so users only see their own rows?

    Enable row level security on the table, then create policies for select, insert, update and delete that compare the owner column with (select auth.uid()), for example using ((select auth.uid()) = user_id). Add with check on insert and update so users cannot create or move rows to someone else.

    Why use (select auth.uid()) instead of auth.uid() in policies?

    Wrapping auth.uid() in a select lets Postgres evaluate it once per query instead of once per row, which Supabase recommends for performance on larger tables. The result is the same.

    How do I let anyone submit a form but not read the submissions in Supabase?

    Enable RLS, grant only insert to anon and authenticated, and add an insert policy with check (true) and no select policy. In the app, insert without chaining .select(), because reading the row back is not allowed.

    Do I need GRANT statements as well as RLS policies in Supabase?

    For tables created after 30 October 2026 in existing projects, yes: new tables are not granted to anon and authenticated automatically, so the Data API cannot reach them until you grant access. RLS policies then decide which rows each user can see.
